# 维护

维护让词表和内容随时间保持可信。它在[治理](governance.md)授权之下运行：治理规定政策、决策权和阈值复核，维护按规则执行。维护由一个循环中的六个要素组成。

```
对象 ──有状态──▶ 指标 ──达到阈值──▶ 触发 ──▶ 动作 ──▶ 审计追踪
```

本文按这六个要素组织。“指标”“阈值”“监控”的用法依据 ISO 15489-1 §6.4 的监控与评价。来源复核、`candidate` 概念记录转正、断言复核、剩余监控和发版都是这个循环的实例，不另立规则。

## 对象与状态

维护作用于以下六类对象，每类对象有自己的状态。

| 对象 | 在哪 | 状态 | 说明 |
|---|---|---|---|
| 来源实体 | `entities.yaml`，`kind` 为 standard／publication | `tier`：de-jure／de-facto／vendor／archival | 分档见[命名实体词表](entities.md)；de-facto 和 vendor 只作入口和例证，不作定义来源，vendor 的接口文档不进概念文和设计文档 |
| 概念记录 | `topics.yaml` | `unassigned`／`candidate`／`active`／`deprecated` | 见[主题词表设计](topics.md) |
| 命名实体记录 | `entities.yaml` | `candidate`／`active`／`deprecated` | 见[命名实体词表](entities.md) |
| 断言 | 各词表的人工赋值字段 | `basis`：有依据／`self` | 见下节 |
| 内容单元 | 知识库 | `draft`／`active`／`deprecated` | 见[内容模型](content-model.md)；不删，处置决定在该文档中 |
| 词表版本 | 各词表的 `version` 块 | 当前版 | 见[词表版本](versioning.md) |

### 断言

人工赋值字段的值不是从来源直接复制，而是人作出的判断。designation 的准入依据只回答它能否被项目采用；本节的 `basis` 回答具体字段值或关系为什么成立。两项门禁相互独立：形式有依据不能证明断言成立，断言有依据也不能替代形式依据。

人工赋值字段的清单以本表为准，各词表设计只引用。

| 词表 | 人工赋值字段 |
|---|---|
| 主题词表 | 本地概念的 `broader`、`related`、`scope`；复制概念之间的合并（同名归一） |
| 命名实体词表 | `subjects`、`form`（多个 Wikidata 类取一个时）、`scope`、`vendor` |
| 内容单元 | `subject`、`type` |

复制值不属于人工判断：`source` 非 `self` 的 `broader`、`match` 和 `label` 不记断言依据。

人工赋值字段旁边记录 `basis`。

```yaml
- id: eslint
  subjects: [tools-and-environments]
  basis:
    subjects: cs2023:SE-Tools#3        # 来源 id + 条目 + 位置：SE-Tools 主题 3“静态和动态分析工具”
- id: uv
  subjects: [tools-and-environments]
  basis:
    subjects: self                      # 没核到依据
```

| `basis` 的值 | 含义 |
|---|---|
| `<来源 id>:<条目>[#<位置>]` | 在该来源的相应条目中核到了支持判断的文字 |
| `<来源 id>:scope` | 来源自身的范围声明支持判断 |
| `wikidata:<Q 号>/P31` | `form` 取自该条目的 instance of；多个值时全部记录，不挑选 |
| `self` | 本库判断，尚未核到外部依据 |

记录中只要有一项 `basis: self`，`status` 就不得为 `active`。把 `self` 改为有依据只能靠核到来源文字，不能靠“长期使用没有问题”。核到文字后批准属于 AI 可直接做的一级，判断本身属于二级，见[治理](governance.md)的决策权。

## 指标

指标是脚本可以计算或外部可以通知的量。

| 类 | 指标 | 对象 | 来自 |
|---|---|---|---|
| 计数 | 被内容单元引用的次数 | 概念记录、命名实体记录 | 内容单元的 `subject`、`entities`（Z39.19 §11.1.3.4 b） |
| 计数 | 未标引概念记录数及占比 | 概念记录 | `status: unassigned` |
| 计数 | `self` 断言数及占比 | 断言 | `basis` |
| 计数 | 处于 `candidate` 状态时经过的编辑审核次数 | 概念记录、命名实体记录 | `added` 与审核日期 |
| 计数 | “其他”类目的下位概念数 | 概念记录 | GB/T “其他学科”等剩余类目 |
| 计数 | 候选识别器报告的独立字符串数、总出现次数和出现文件数 | 带上下文的未解析字符串线索 | 公开的抽取、排除、标签比较和规范化规则（Z39.19 §11.1.3.4 a） |
| 计数 | 没有匹配任何概念的检索次数 | 带上下文的未解析字符串线索 | 应用提供的检索记录（Z39.19 §11.1.3.4 c） |
| 时间 | 距上次复核的月数 | 来源实体 | `checked` |
| 时间 | 距上次编辑审核的月数 | 词表 | `signals.yaml` |
| 外部事件 | 来源发布新版 | 来源实体 | `watch` 探测点 |
| 外部事件 | 链接失效 | 来源实体、引用 | 链接检查 |

脚本输出和人工提名后的 `candidate` 概念记录分别计量。未解析字符串保留来源上下文，只是复核线索；它不会因未匹配而直接成为项目采用的名称、概念、关系或结构结论。

未标引、`self`、长期 `candidate` 和“其他”四项对应 Star 与 Bowker 的剩余类目：分类没有安放好的内容，其规模和增长是分类失效的指标。维护不消灭这些内容，而是持续监控。每个指标的历次值记入 `signals.yaml`。

引用次数类指标须读取知识库内容，由应用映射提供。首个映射落地前，这些指标不触发，见[决定记录](decisions/form-independence.md)。

## 阈值

所有数字只在本节出现，其他文档和脚本引用本表。除标明外部依据的项目外，其余均为本库估值，须在首轮维护，即第一次编辑审核完成后校准。

| 指标 | 阈值 | 依据 |
|---|---|---|
| 引用次数，`unassigned` → `active` | 1 次，或有下位 | 本库 |
| 引用次数，`candidate` → `active` | ≥ 3 次，且有 `scope`，且通过审核四问，且 `basis` 无 `self` | 本库 |
| `candidate` 概念记录删除资格 | 引用为 0 连续两次编辑审核 | 本库 |
| 编辑审核触发 | `candidate` 记录攒到 20 个，或距上次审核满 12 个月 | 本库 |
| 某节点下 `self` 断言 | ≥ 5 | 本库 |
| 某节点下 `candidate` 记录 | ≥ 5 | 本库 |
| “其他”类目下位 | ≥ 3 | 本库 |
| 某顶层未标引占比 | 连续两次编辑审核（约 12 个月）无变化 | 本库 |
| 来源复核，de-jure | 24 个月，或发新版 | 本库 |
| 来源复核，de-facto | 12 个月 | 本库 |
| 来源复核，vendor | 6 个月 | 本库 |
| 来源复核，archival | 不复核内容 | 内容固定 |
| 链接检查 | 3 个月，所有档相同 | 本库 |
| 过度使用的概念 | 单个概念的引用占全部引用 ≥ 10% | Z39.19 §11.3.1.3：过度与过少使用都是修改或删除的复审线索；数字为本库估值 |

## 触发与动作

指标达到阈值后触发动作。动作只允许以下集合：**批准、废弃、删除、拆分、合并、找依据、复核来源、注明不覆盖、发版**。每个动作所属的决策权级别见[治理](governance.md)。

| 指标达到阈值 | 动作 |
|---|---|
| `candidate` 概念记录达到批准条件 | 批准：`candidate` → `active`（Z39.19 §11.1.6 approved） |
| `unassigned` 概念记录被引用 | 批准：`unassigned` → `active` |
| 本地 `candidate` 概念记录引用为 0 连续两次审核 | 只取得删除资格；AI 列清单，人批准后才能删除。其他状态和单个表示形式不继承该资格 |
| 某节点下 `self` ≥ 5 或 `candidate` 记录 ≥ 5 | 拆分：该节点需要下一级类目；先找文献依据，有依据才建 |
| “其他”类目下位 ≥ 3 | 拆分：寻找正式类目；找不到的保留在“其他”并写明 |
| 某顶层未标引占比长期不变 | 注明不覆盖：在顶层概念的 `scope` 写明原因；或承认尚未覆盖，不修改结构 |
| 过度使用的概念 | 拆分为更具体的概念，或增加下位概念（Z39.19 §11.3.1.3） |
| 两个概念被判断为同一个 | 合并：保留一个，另一个转为 `deprecated` 并记录 `replaced_by` |
| `self` 断言 | 找依据：核对来源文字；核到后修改 `basis`，记录才可转正 |
| 来源复核到期或发布新版 | 复核来源，见下文 |
| 链接失效 | 找官方新地址，其次 DOI／arXiv，最后 archive.org 快照 |
| 一批批准、废弃、来源改版后的增删改 | 发版，见[词表版本](versioning.md)；只补 `scope`、`alt`、`match` 不触发 |

### 候选的产生

输入线索与 `candidate` 概念记录按以下顺序处理。

1. 脚本在指定位置识别带来源上下文的字符串或名词短语。标题、加粗内容和中文引号纳入；代码和链接目标排除；规范化只使用明确批准的规则。
2. 脚本把识别结果与三份词表中已登记的首选、替代和隐藏标签比较。
3. 已匹配结果按概念 ID 复核；未解析字符串留在脚本输出中，并分别记录独立字符串数、总出现次数、文件数和上下文。
4. 人工可以从未解析结果或其他材料中提名。提名后先判断目标概念，再核验表示形式的采用依据。
5. 需要新增主题概念时，只有概念判断和依据核验完成后，才建立 `status: candidate` 的概念记录；经核验的表示形式作为记录标签保存，`origin` 指向首次出现的内容单元。输入若表示命名实体，另按[命名实体词表](entities.md)处理。

未被提名的字符串留在脚本输出中，等待后续复核。未命中的检索同样只提供带上下文的线索；是否进入概念记录仍由人工判断。表示形式的独立候选生命周期继续延期。

### 候选的审核

批准 `candidate` 概念记录前，按 Z39.19 §11.3.1.1 的四问审核。

1. 目标概念已由一个现有概念覆盖，或可由多个现有概念组合表达吗？如果可以，不新建概念记录，转入独立的表示形式审核。
2. 目标概念是否需要 `scope`？
3. 经准入核验的首选、替代和隐藏标签怎样记录，`label.zh`、`label.en` 和 id 是否符合现行规则？
4. 目标概念与现有概念之间的 `broader`、`related` 怎样建立？

概念覆盖判断和表示形式审核不能合并。同义表示不能制造概念缺口，同形异义也不能制造概念覆盖；本节接受程序中的 `candidate` 状态只作用于概念记录，不作用于表示形式。

### 来源的复核

1. 打开来源，确认引用事实仍在且未改
2. 有新版时读取变更说明，判断是否影响本库引用部分；有影响就修改正文，无影响只更新实体的 `version` 和 `checked`
3. 来源被撤销或替代时寻找替代来源并修改引用；找不到时把断言标为“来源已失效”，不删除
4. 一并复核 `basis` 引用该来源的断言
5. 更新 `checked`

链接存活与内容有效分开检查：前者由脚本处理，所有档相同；后者由人工按 `tier` 处理。archival 档写入时使用 DOI、arXiv 或带日期的永久链接。

每个 de-jure 实体在 `watch` 中登记一个可脚本化的新版探测点。

| 发布方 | 探测点 | 检查内容 |
|---|---|---|
| ISO | `https://www.iso.org/standard/<id>.html` | 状态字段（Published／Under review／Withdrawn）和“将被替代”提示。iso.org 对脚本返回 403 时带浏览器 UA，或改用 iTeh 镜像页 |
| GB/T | `std.samr.gov.cn` 详情页 | 标准状态（现行／废止）和替代标准 |
| W3C | `https://www.w3.org/TR/<shortname>/` | “This version”日期和“Latest published version”链接 |
| IETF | `https://www.rfc-editor.org/info/rfc<n>` | Obsoleted by／Updated by |
| NISO | `https://www.niso.org/publications/<id>` | 状态与年份 |

## 审计追踪

审计追踪按下表分层，[治理](governance.md)只引用本节。

| 层 | 记在哪 | 记什么 |
|---|---|---|
| 对象 | 概念和实体的 `history` | 每次状态变化的日期、内容和原因（Z39.19 §11.3.2.2 历史注释） |
| 版本 | `vocab/CHANGELOG.md` | 每版新增、废弃、改名和来源更新；只追加 |
| 规则 | `design/decisions/` | 治理规则本身的变更；ADR 只追加 |
| 维护动作 | `vocab/CHANGELOG.md` 当前版节 | 每次定期复审执行的动作 |
| 指标快照 | `vocab/signals.yaml` | 历次定期复审指标、编辑审核日期和治理年审日期 |

注明不覆盖也是审计追踪。未安放的内容可以被承认，但必须记录。

## 定期复审

| 时点 | 动作 |
|---|---|
| 内容或词表任何改动后 | 运行 `check-topics.py`（校验与指标表）、`check-links.py` |
| 每月 | 运行 de-jure 新版探测脚本 |
| 每 3 个月 | 运行链接存活脚本 |
| `candidate` 记录攒到 20 个，或距上次编辑审核满 12 个月 | 编辑审核；同时读取指标表，对照触发表执行动作；用 `--record` 写快照 |
| 按 `tier` | 复核来源 |
| 动作攒成一批 | 发版 |

人工操作只在定期复审时进行；脚本可以随时运行，指标表在定期复审时读取。链接存活脚本和 de-jure 探测脚本待写，完成前相应两行不执行。

## 指标表

`check-topics.py` 在校验之外输出指标表，每个指标一行：当前值、上次值、阈值和是否触发。历次值保存在 `vocab/signals.yaml`，定期复审用 `--record` 追加快照。每个顶层的未标引数和每个字段的 `self` 数是其中两组。脚本目前只计算词表内部指标。

## 应用映射的分工

怎样读取内容单元正文和字段、从哪里取得检索记录、怎样计算引用次数，由各应用映射回答，见[内容模型](content-model.md)“应用映射的要求”中的相应问题。本文只规定指标、阈值和动作。

## 收录依据

本文件的来源复核回答“事实从哪里来、为什么可信”；[词表的建设与维护](../concepts/vocabulary-construction.md)中的 warrant 回答“某个 designation 为什么可以被采用”。处理来源材料时，还要区分来源中的字符串、字符串所表示的概念、现有概念是否覆盖目标概念，以及表示形式能否被项目采用。

来源中出现一个字符串只提供文献依据线索。人工仍须判断目标概念和现有覆盖，再独立审核表示形式。来源分级本身采用组织依据，即本库获取和信任知识的方式；它不能代替具体概念、形式或断言的核验。

## 待定事项

- 阈值表中标“本库”的全部数字在首轮维护后校准
- 名词短语采用哪种抽取方法；中英混排文本怎样分词
- 表示形式的独立候选生命周期及其外部依据
- 内容单元的 `subject`、`type` 是否记录 `basis`，还是由引用计数代替
- `basis` 条目中“#位置”的写法是否统一为来源自身编号
- 注明不覆盖的节点在 `scope` 中怎样写
- 链接存活脚本和 de-jure 探测脚本待写；概念文与内容单元引用的文献登记为实体，引用处改为实体 id
- 计数类指标在首个应用映射落地前不触发
