# 术语交换 (TBX Export)

状态：草案，未生效。当前没有具名接收方、正式术语发布快照或 TBX 互操作需求，本项目不设计或实现 TBX 导出。

## 草案边界

本草案只记录未来重新评估 TBX 的条件。它不选择 TBX 方言、版本或表示样式，不建立字段映射、损失报告、验证资源、导出命令或发布流程，也不授权创建 TBX 文件。

TBX 的概念关系见[术语数据库](../../concepts/terminology-database.md)，已核官方材料和未读边界见[术语标准](../../sources/terminology-standards.md)。阅读这些材料不等于本库采用 TBX。

## 当前价值

本库内部已经分别使用适合编辑、机器消费和读者阅读的形式：术语编辑源拟使用 YAML，机器快照使用 JSON，读者视图使用 Markdown。当前没有外部系统要求 TBX，也没有证据说明 TBX 能解决现有内部治理、术语准入、来源维护或 Obsidian 映射问题。

因此，当前实现 TBX 只会增加方言选择、映射、信息损失、验证资源和版本维护成本，没有对应消费者价值。

## 触发条件

只有以下条件全部成立，才重新启动设计：

1. 存在具名接收系统、合作方或发布渠道；
2. 接收方说明实际任务，以及现有 JSON 或其他交付形式为什么不能满足；
3. 本库已经形成正式术语数据和可发布快照；
4. 接收方给出支持的 TBX 代际、方言、版本和表示样式；
5. 双方确认必须交换的概念、语言、定义、术语、状态和稳定身份；
6. 可以逐项说明内部字段的映射、保留、损失和阻断条件；
7. 可以取得并合法固定所需验证资源、版本和许可材料。

任一条件缺失时，本草案继续保持未生效，不以“通用交换”或未来可能使用代替真实需求。

## 设计边界

若触发条件以后成立，设计仍须遵守以下边界：

- 内部术语模型和发布快照保持唯一事实来源；
- TBX 只作为发布后的交换物；
- 不提供 TBX 导入、往返编辑或从 TBX 恢复内部治理记录；
- 不因现成方言允许某个数据类目，就假定它与内部字段语义相同；
- 先比较接收方要求与 TBX-Core、TBX-Min、TBX-Basic 等候选，再决定方言；
- DCA／DCT 作为表示样式单独选择，不能由方言名称自动推出；
- 未映射信息必须可审计，未知字段不得静默丢失。

## 待定事项

- 谁是第一个真实接收方；
- 交换任务和现有 JSON 的缺口是什么；
- 接收方要求哪个 TBX 版本、方言和样式；
- 哪些内部值是交换必需值；
- 可接受的信息损失边界是什么；
- 验证资源和发行资产能否固定并合法再分发。
