# 实体类别职责

状态：草案，未生效。

## 状态边界

本文只提出命名实体类别与相邻字段的职责模型，不修改[命名实体词表设计](../entities.md)、正式实体数据、来源数据、schema 或校验器。推荐采用复核方案 B，但该推荐只形成 L2 提案方向，不批准任何新 `kind`、记录迁移、来源用途或 L3 事项。

类别、外部分类事实、实体 `form`、内容载体、主题归属、责任关系、产品与版本身份、来源实体资格和来源用途分别决定。任一项都不能从名称、URL、版本字符串、发布方或另一字段自动推出。

## 依据边界

- [Wikidata P31](https://www.wikidata.org/wiki/Property:P31)连接个体与类，[P279](https://www.wikidata.org/wiki/Property:P279)连接类与更宽类；P31 本身不可传递，项目是否允许经 P279 投影须由 L2 决定。
- [Q317623](https://www.wikidata.org/wiki/Q317623)不能因材料被项目用作来源，就自动覆盖知识体系、分类系统、知识库、文档站、课程、排名或词表。
- [Q591041](https://www.wikidata.org/wiki/Q591041)是较窄的 scientific publication，[Q732577](https://www.wikidata.org/wiki/Q732577)是更宽外部类线索；外部宽窄关系不自动批准本项目改类。
- [Wikidata Books 项目说明](https://www.wikidata.org/wiki/Wikidata:WikiProject_Books)只直接支持书目中的作品与版本分离。软件、标准、课程、网站和数据集仍须项目逐项决定身份判据。
- 23 条映射的全部 P279 闭包和 38 条无映射记录的当前外部身份尚未逐条核完；本草案不依赖这些未读事实迁移数据。

## 职责分工

| 对象 | 应承担的职责 | 不承担的职责 |
|---|---|---|
| 项目 `kind` | 把唯一个体投影到一个获准外部宽类，供稳定筛选 | 载体、主题、用途、发布方、产品关系或来源资格 |
| 外部分类事实 | 保存直接 P31、必要 P279 路径、核对日期和冲突 | 自动写入正式 `kind` 或实体 `form` |
| 实体 `form` | 职责、基数和值域仍待决定；现值只作历史库存 | 内容载体、第二个 `kind` 或产品身份 |
| 内容 `form` | 按[内容模型](../content-model.md)表示内容单元的呈现或教学活动载体 | 软件类别、接口或分发单位 |
| `subjects` | 表示实体与主题概念的发现关系 | 类别、结构位置、来源角色或产品系列 |
| `vendor` | 表示获准的产品责任关系 | 作者、出版者、所有者、来源资格或全部责任 |
| `creator` | 表示获准的创作责任关系 | 产品供应方、主题或类别 |
| 产品与版本关系 | 区分产品、系列、具体发布物、版次和快照的身份 | 由名称后缀、URL 或 `version` 自动决定拆分 |
| 来源实体资格 | 表示某个材料身份可以被来源引用 | 自动批准用途、档位或具体关系 |
| 来源用途 | 表示某来源获准承担的用途角色 | 实体类别、身份、具体派生或映射 |

## 方案比较

| 方案 | 核心做法 | 收益 | 代价 |
|---|---|---|---|
| A | 保持单一宽 `kind`、单一具体 `form`，来源资格继续绑定两类 | 无即时迁移 | 混合职责、多 P31 丢失、来源与类别耦合继续累积 |
| B | 保留一个获准宽 `kind` 作为项目投影；完整保存外部 P31／P279 证据；冻结实体 `form`；把主题、责任、产品层级和来源职责分开 | 不新增类别，保留外部事实，支持逐批迁移和稳定身份 | 需要 L2 明确投影、字段和身份关系，并同步消费者 |
| C | 取消稳定宽类投影，查询时动态依赖全部外部 P31 | 外部细节丰富 | 外部变化直接影响本库；38 条无映射记录无稳定分类；来源和版本问题仍未解决 |

## 推荐方案

推荐方案 B。一个项目 `kind` 只承担稳定宽类投影；直接 P31 与必要 P279 路径作为完整、带日期、逐项可核的外部事实保存。多路径冲突交人决定，P31 之间不得互相传递。

实体 `form` 在职责获准前冻结，不补值、不数组化、不改成 Q 号，也不解释为内容载体。`subjects`、`vendor` 和 `creator` 分别取证。产品、系列、具体版本、课程届次、标准分部、网站集合和快照先决定身份层级，再决定关系。普通版本更新不自动改变稳定 ID。

来源实体资格与 `kind` 解耦，但只有来源治理规则、兼容消费者和迁移回退同时获准后才能实施。来源身份不批准用途，用途批准也不产生具体 `basis`、`source` 或 `match`。

## 替代方案

方案 A 可作为正式规则未改变期间的兼容现状，但不得继续扩写混合职责字段。方案 C 只适合作为外部证据查询方式，不作为正式分类机制；当前没有细粒度动态类别消费者，不采用它的代价可接受。

## 不采后果

- 不采用方案 B，会继续让 `kind`、实体 `form`、外部分类事实和来源资格互相代偿。
- 不新增细粒度 `kind`，会失去部分直接分类查询，但当前没有相应正式消费者；该代价低于类别膨胀和零自定风险。
- 不立即迁移 15 条疑虑，会保留已知含混；但在身份判据未定时迁移，更容易错拆、错并或切断引用。
- 不把来源资格与类别解耦，会使未来类别修正继续威胁 31 条来源身份和现行引用。

## 影响范围

若方案 B 以后获准，可能影响 `design/entities.md`、`design/governance.md`、维护与来源设计、来源治理草案、实体和来源 schema、`vocab/entities.yaml`、`vocab/sources.yaml`、校验器以及类别筛选消费者。正式迁移前须冻结 61 个 ID、31 个来源身份和全部反向引用，并在应用前后双向对账。

本草案当前不修改上述对象。`kind`、身份层级、实体 `form`、`subjects`、`vendor`、`creator`、来源资格、用途角色和 `tier` 必须分列候选，不共享批准状态。

## 权限门禁

### 提案门禁

- 直接 P31 与经 P279 投影的统一规则，以及现行类别的保留方式；
- publication 外部宽类和来源样本的逐条分类；
- 实体 `form` 的职责、基数、值域和去留；
- 产品、系列、版本、届次、分部、集合和快照的身份判据；
- `vendor`、`creator`、`subjects` 的关系语义和逐值依据；
- 来源实体资格与用途角色的解耦契约；
- 61 条记录的逐项处置和 15 条身份疑虑的稳定 ID 方案；
- schema、校验、迁移批次、消费者契约和回退。

### 保留门禁

- 任一来源 `tier` 改档；
- 草案生效、来源草案生效、正式数据切换、消费者启用、发版和回滚执行。

## 生效条件

本草案只有在人批准方案 B 的规则提案、外部类与 designation 均有合格依据、一般实体与来源实体契约闭合、逐项候选和引用对账完成、兼容消费者先于来源改类可用、应用后验证与补偿回滚具备，并另行作出草案生效决定后，才可并入正式设计。任何单条记录的 L2 决定不使整份草案生效。

## 错误代价

| 错误 | 后果 | 代价 |
|---|---|---|
| 把来源用途当类别 | 文档站、课程、排名或词表被误当 technical standard | 高 |
| 把具体 P31 塞进实体 `form` | 接口、包、框架、库和工具混成同一面 | 高 |
| 把内容载体用于实体 | 两套值域互相污染 | 高 |
| 把 `subjects` 当类别 | 学科归属替代本体类别 | 高 |
| 把 vendor 当 creator | 产品责任、作者、发布者和所有者混同 | 高 |
| 把版本字符串当身份规则 | 稳定 ID、历史和替代链损坏 | 高 |
| 改类时同步改来源资格 | 现行来源登记和下游引用失效 | 最高 |
| 由 Wikidata 变化自动写值 | 外部编辑绕过项目决策权 | 最高 |
| 为查询新增无需求类别 | 类别枚举膨胀并继续漂移职责 | 中高 |
