# 第一原理与设计理由 (First Principles and Design Rationale)

## 定义

**第一原理**是一个领域里不能再从别的命题推出、只能作为起点的命题。亚里士多德《后分析篇》的论证：如果每个知识都要靠证明，证明的前提又要靠证明，那么要么无限倒退，要么循环。两者都不可接受，所以证明链必须终止于**不可证明但可知**的起点，他称为 ἀρχή(archē，本原)。这些起点必须为真、居先、无中介、比结论更可知，并且是结论的原因。

作为方法，“从第一原理出发”就是：从不可再分的前提推导，而不是类比已有的做法。

**设计理由**(design rationale)是记录“为什么这样决定”而不只是“决定了什么”。两者的关系：第一原理是设计理由里最深的一层——追问“为什么”追到不能再追的地方。

## 解决的问题

| 问题 | 例子 | 第一原理 / 设计理由的处理 |
|---|---|---|
| 规则靠症状堆出来，彼此无关 | 标题出问题加一条标题规则，用词出问题加一条用词规则 | 找到共同的根（为读者写），所有规则从根推出 |
| 无法判断新规则该不该加 | “要不要禁止加粗词当标题？” | 能从已有原理推出就加，推不出就不加 |
| 决定的理由随时间丢失 | 半年后不知道当初为什么把时间降级成元数据字段 | 理由和决定一起记录 |
| 新人（或未来的自己）面对旧决定只能盲从或盲改 | 不知道复制的层级为什么要求完整，随手删了未标引的概念 | 理由可查，改之前能判断前提是否还成立 |
| 方法来自类比，不知道它在新场景是否成立 | 照抄图书馆的做法到个人知识库 | 回到原理，看前提在新场景是否还满足 |

## 设计理由的两个传统

### IBIS

Kunz 与 Rittel 1970 年提出，为应对“棘手问题”（wicked problem）——定义不清、没有唯一正解、多方视角冲突的问题。结构是三种节点：

```
议题 (issue)      ← 要回答的问题
 └─ 立场 (position)   ← 对议题的一个回答
     ├─ 支持论据 (argument pro)
     └─ 反对论据 (argument con)
```

IBIS 记录的是**论证过程**，不只是结论：哪些立场被提出、各有什么论据、最终为什么选这个。

### ADR

Nygard 2011 年提出的架构决策记录（Architecture Decision Record），是 IBIS 思想在软件工程里的轻量实践。每个决定一个短文件，五个字段：

| 字段 | 内容 |
|---|---|
| 标题 | 名词短语 |
| 背景 | 中立地描述当时的各方力量：技术、组织、项目约束 |
| 决定 | 主动语态，“我们将……” |
| 状态 | 提议 / 采纳 / 废弃 / 被替代 |
| 后果 | 所有结果，好的坏的中性的 |

关键规则：**旧记录不删不改**。决定被推翻时，旧记录标“被替代”并指向新记录。这和受控词表里废词不删的做法是同一个原理：历史可追溯。

Nygard 给的动机：项目里最难追踪的是决定背后的动机；没有记录，后来者要么盲从（环境变了也不敢改），要么盲改（破坏了当初保护的东西）。

## 第一原理与设计理由的关系

```
设计理由       为什么这样决定
   │
   ├─ 直接理由       因为要解决 X 问题
   ├─ 再上一层       因为 X 问题来自 Y 约束
   └─ 第一原理       因为 Z 是这个领域不可再推的前提
```

ADR 通常只记到直接理由。把每个方法追到第一原理，是更深一层的设计理由——代价高，收益是：**原理能当判定器**，新规则能否从它推出，一眼可判。

## 在知识库中的用法

1. 采用任何方法或范式前，先找它的第一原理和来源。找不到的方法是别人的习惯，不是可以依赖的根
2. 本库的设计文档按 ADR 的精神记录理由，不只记录规则。规则被推翻时旧文不删，标被替代
3. 新规则的准入标准：能从已登记的原理推出。推不出的，要么是原理缺了一条（补登记），要么是这条规则不该有
4. 不必每个决定都追到哲学层。追到“这个领域公认的前提”即可；再往下是哲学史，与设计无关
