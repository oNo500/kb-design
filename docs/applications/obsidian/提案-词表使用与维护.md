# 词表使用与维护

本方案规定以 PARA 组织 Obsidian 知识库，词条为其中的文章选择、引用和检索提供支持。库内只交付知识内容及必要的写作配套，工程数据保存在库外。开发环境不等于词表浏览功能，本轮不切换正式库或自动迁移旧库。

## 内容结构

PARA 的四个主要区域采用 `01-projects/`、`02-areas/`、`03-resources/`、`04-archives/`。它们表示项目、持续责任领域、主题资源和不再活跃的内容；`00-inbox/` 是前置收集区，不是第五个 PARA 核心类别。方法依据 [Tiago Forte 原文](https://fortelabs.com/blog/para/)，具体编号和小写目录名是本应用的表示选择，不宣称为标准强制要求。

`05-vocabulary/` 保存各区共同引用的知识条目，`06-views/`、`07-templates/`、`08-attachments/` 分别服务导航、写作和附件。首页为 `home.md`，顶层编号不改变内部目录和文件名。用户可以在 PARA 四区继续建立具体项目或责任领域的目录，不从这些目录名称自动推断主题、实体、文档类型或内容状态。

同一对象可以被多个区域的文章引用。项目归档不归档对应词条，不改变文章 UUID，也不自动把 status 改为 deprecated。主题关系用于跨目录检索，不能被文件夹位置替代。

PARA 可以保存文章和一般资料。声明应用 `identifier` 的记录进入文章字段校验；没有该声明的文件保留，并明确列为未登记、未检查，不推断它一定属于某种资料，也不计作通过。删去 identifier 的文章也会出现在这份清单中。已声明但无效的身份及其他必填字段仍按原约束报错；识别到字段不等于正式采纳或发布。

## 使用目的

使用者应能按名称或别名找到条目，理解含义，在正确的文章字段中保存引用，再按这些引用找回文章。条目详情按需读取，不要求先浏览整份词表。

| 文章需要表达的内容 | 字段及所用数据 |
| --- | --- |
| 讨论什么主题 | `subject`，引用适用的概念 |
| 涉及哪个具体对象 | `entities`，引用人物、组织、软件等实体 |
| 文章的用途、作者立场与载体 | `type`、`genre`、`form`，分别引用各自已采用的值域 |
| 引用了哪份文献 | `references`，引用已登记且适用的文献记录 |

“受控选项”描述字段的取值角色，不是与概念、实体并列的第三类对象。类型、体裁、载体的记录按现有内容模型表示为概念；它们不会因为同名就与主题概念合并。

## 职责分工

| 对象 | 维护责任 |
| --- | --- |
| 概念、实体、名称、定义、关系与来源 | 维护端按已有模型及权限修改权威数据 |
| 应用条目、身份对应与查询数据 | 应用工具从明确版本生成，保持源身份与语义 |
| 文章正文、所选引用、私人视图与批注 | 使用者在 Obsidian 中维护 |
| 缺词、错词或应用障碍 | 保留问题证据，交相应责任方处理 |

Obsidian 中的条目供使用，不成为第二个词表编辑源。页面的人工改动不回写原始词表；词表刷新也不覆盖 PARA 内容。初建产生的首页、视图和模板随后由使用者维护；整个运行中的知识库不能当作可删除重建的构建目录。

## 文章操作

### 条目选择

先确定文章字段，再按名称或别名查找。候选至少返回可读名称、对象或值域类型、简短定义或范围、身份、链接和可用条件。名称精确匹配优先于前缀与包含匹配；排序只影响展示，不决定概念是否相同。

同一字段中存在多个准确同名结果时，必须返回候选供辨认。用户或 AI 提供明确身份后才能选定；不能按返回顺序、名称相似或目录邻近替代判断。隐藏名保留在源数据中，不作为默认推荐选项。

选择过程中如需进一步区分，再读取完整定义、范围、关系及来源。缺少定义时如实返回缺失；不能从标签、上位概念、名称说明或模型知识补造定义。

### 文章引用

文章保存对选定对象的明确引用；链接显示可读名称，身份由条目中的原标识和交付对应确认。使用同一概念的中英文名称时，仍引用同一身份；同名不同对象分别引用。

普通主题标引、实体涉及和文献引用的语义分别保留。选中实体不自动补出主题，正文提及也不自动成为元数据。写作手法用于组织文章时不必填入 `subject`，只有文章讨论该手法时才按内容选作主题。

名称选择与最终写入之间，工具仍须按原身份重新核对对象种类、可用条件和当前版本。名称解析成功不能替代文章字段校验。

### 文章检索

按 `subject`、`entities`、类型等字段中已保存的引用查找文章。名称和别名可作为查询入口，先解析到明确身份，再匹配引用；全文搜索和 Backlinks 另作发现手段，不混为同一种关系或计数。

主题查询区分直接标引与包含下位概念。下位范围只使用明确的 `broader`／`narrower` 关系，多条路径命中同一文章时按文章身份去重；不把全部上位概念写回文章，也不将层级推导为实体事实。

## 条目表示

条目文件承担原生链接目标。新文件名由显示名称生成，英文小写，空格与下划线改为中划线；title、别名和原身份保持原值。同名文件的处理和刷新时的路径稳定性由[导出合同](提案-Obsidian%20导出与导入.md#路径规则)统一规定。

页面主要提供名称、必要使用条件、定义、范围、关系和简短来源。完整源属性、XL 名称身份、原始文件和校验细节保留在库外工程数据中，按需回查；不在每个条目中展开完整工程清单或长篇查询代码。

查询工具默认返回摘要，需要详情时显式读取。摘要、详情和页面都来自同一份固定交付，不能另维护一份独立概念资料。语义简化仅作用于展示；原数据的关系种类、语言、出处和版本不因此减少。

## 版本更新

维护端交付明确版本及变化说明，使用端显式选择更新时间。生成、安装、正式采用和发布分别记录，不能互相代替。

常规刷新核对当前基准、候选版本和用户改动，只更新 `05-vocabulary` 与其库外交付记录。已有身份保持已安装路径；名称或译文更新不会隐式重命名全部页面。第 2 版实例迁移到编号布局须单独执行，不能借普通刷新完成。退出对象保留旧引用入口，合并或拆分不自动替换文章引用。具体版本引用保留所引版本，不能静默改读当前描述。

用户确需重命名时，必须连同 Obsidian 内部链接、身份对应、查询路径和交付清单整体处理。原生 CLI 的链接更新能力不能替代应用清单更新；常规刷新不承担这一迁移。

## 问题反馈

问题记录保存发生条件、对象与文章位置、数据和应用版本、预期与实际结果、证据及影响，区分事实、假设和待核问题。

数据问题交维护端核对；应用问题在实践层解决。怀疑设计存在缺陷时，问题记录先作为研究对象，再核对标准与成熟方案，按治理权限决定是否修改设计。诊断和研究结果本身不使新规则生效。

## 验收依据

验收必须覆盖按名称找到正确对象、区分同名、选择后保存正确身份、按引用找回文章，以及更新后引用仍可解释。文件生成成功、字段通过或搜索有结果都不能单独证明这些操作可用。

数据语义遵循[词表整体设计](../../model/vocabulary/设计-词表整体设计.md)、[实体设计](../../model/entities/设计-命名实体词表.md)和[内容模型](../../model/content/设计-内容模型.md)。本方案采用已登记的 [Application Profile](../shared/概念-Application%20Profile.md) 方法，表示与工程边界遵循[共同适配要求](../shared/设计-适配要求.md)。

[Obsidian Properties](https://obsidian.md/help/properties)提供属性与内部链接能力；SKOS 提供概念、名称和关系的表示，[SKOS Primer 的标引示例](https://www.w3.org/TR/skos-primer/#secindexing)说明内容对概念的引用。具体目录、文件名、查询结果和操作入口是项目选择，不宣称由标准直接规定。

完整字段见[Obsidian 元数据](提案-Obsidian%20元数据.md)，输入、文件管理和恢复见[导出与导入](提案-Obsidian%20导出与导入.md)。命令、运行版本及使用结果在[独立应用包](../../../apps/obsidian-rdf/README.md)维护。
