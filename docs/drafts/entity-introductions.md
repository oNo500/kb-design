# 实体介绍写作

状态：草案，未生效。本文依据用户在 2026-09-05 对实体介绍、第一性原理、可选实践内容和收录边界的要求形成设计提案；批准起草不等于批准生效。

## 设计目的

实体介绍帮助读者认识一个具体对象，判断它与自己的问题有什么关系，并找到继续学习或使用的入口。文章的价值来自必要解释、依据明确的判断和经过选择的资源，不来自对官网的覆盖程度。

本文约束写作，不新增实体类别、文档类型、体裁、字段或术语。文中小节名称是普通写作提示，不作为词表值；“第一性原理”沿用用户提出的要求，以下用具体问题落实，不宣称另行采用了一套外部标准或已登记方法。

## 现行依据

以下依据分别约束对象、元数据、文字和效力。

| 依据 | 适用内容 | 不由该依据推出的结论 |
|---|---|---|
| [实体设计](../design/model/entities.md) | 实体是具体对象，与主题概念分开 | 登记一个实体不要求立即为它生成文章 |
| [内容模型](../design/model/content-model.md) | 一篇一个主题；类型、体裁、身份与状态的约束 | 元数据合法不表示正文值得收录 |
| [写作规则](../design/governance/writing.md) | 单一读者需求、标题、术语、引用与整篇重写 | 不能把本文新增要求冒称为外部标准条款 |
| [治理规则](../design/governance/governance.md) | 术语准入、规则变更与草案生效权限 | 本文及示例不批准新对象、关系或状态 |
| 本次用户要求 | 必须解释问题与原理；避免重复官网；实践与偏好有材料才写 | 不授权 AI 代写用户经验或推测个人偏好 |

逐节要求和收录判据是上述现行约束与本次用户需求形成的项目提案，尚不是现行义务。

## 内容分工

一个实体可以有一篇入口概述，以及多篇围绕具体任务的教程、操作指南、参考、排障或实践笔记。入口概述负责整体认识，相关笔记负责可独立使用的细节；不将一实体一篇入口理解为一实体只能有一篇内容。

介绍以理解对象为主要目的时使用现有 `explanation`。`genre` 根据全文实际立场选择：事实转述可为 `background`，比较与推断可为 `analysis`。不能仅因存在引用就认定为背景，也不能仅因有一个建议句就改变全文体裁。独立的操作任务或评价若成为主要目的，应另写相应内容，不以“实体介绍”为理由混合全部类型。

`type` 与 `genre` 继续各填一个；将体裁改为选填不在本提案范围。长文不填 `form`，认知层级只在用户作出自评时填写。新增文章保持建立器允许的 `draft`，本文不批准转为 `active`。

标题提到某实体不自动生成受控实体引用。受控引用须指向已登记对象；未登记时按现行内容规则处理，不为了写介绍直接修改词表。生成的实体参考页与个人介绍分开，介绍不写入受管理的词表参考正文。

## 收录条件

动笔前先说明读者需要解决的认识或判断问题，随后确定文章提供的解释、比较或参考入口。只有对象名称、官网链接和官网摘要时，保留资料入口即可，不扩写成完整介绍。

拟收录的入口概述须同时满足：

- 对象与讨论范围明确，不混淆产品、厂商、版本和文档。
- 能完成下文“问题与原理”的基本解释；无法完成时继续收集材料，不用空泛文字填满。
- 相比直接访问官网，至少提供有依据的问题解释、条件比较或带选择理由的资源入口。
- 必要事实可以追溯；未知事项不影响核心认识，或已经据此收窄结论。

来源无法访问时，如实说明具体缺失，不视为不存在；未知的外围细节可以省略。核心机制或关键前提缺少依据时，材料留待整理，不宣称介绍已完成。

## 章节要求

表中要求适用于拟按本文完成的介绍。“可选”表示缺少合格材料时整节省略，不留待填标题。章节名称可按对象使用常见表达调整，但不得隐藏必写内容。此表是选择与检查范围，不是必须全部复制的空白模板。

| 小节 | 必要性 | 应回答的问题 | 内容边界 |
|---|---|---|---|
| 概述 | 必写 | 对象是什么，属于什么，读者为什么需要认识它 | 简要定位并给权威入口；不展开功能清单和长篇历史 |
| 背景 | 可选 | 哪些形成背景或关键变化影响今天的理解 | 只写有解释作用的背景；简短时并入概述，不重复 |
| 问题与原理 | 必写 | 原始问题、必要条件、解决方式及其因果联系是什么 | 按下一节展开；不以功能列表、宣传语或创始故事替代 |
| 用途 | 可选 | 在哪些具体任务中能得到什么结果 | 原理尚未说明清楚的场景才单列；假设示例明确标示，不冒充用户经历 |
| 主要特点 | 可选 | 哪些设计选择影响效果、使用或维护 | 每项解释作用与代价；与问题与原理重复时并入，不穷举功能 |
| 适用范围 | 必写 | 哪些条件下有用，前置知识、环境或资源是什么 | 解释适合的原因；不能只列用户群体 |
| 局限性 | 必写 | 哪些问题不能解决，成立条件与代价是什么 | 区分对象限制、版本限制与使用方式；内容少时与适用范围合为“适用边界” |
| 推荐实践 | 可选 | 有哪些有依据的做法，分别解决什么问题 | 说明适用条件、来源和代价；操作细节另文，不无条件声称“最佳” |
| 个人偏好 | 可选 | 用户实际选择了什么，接受哪些取舍 | 只根据用户表达或经确认的实践写；没有选择就省略，文件现状不自动等于偏好 |
| 实践记录 | 可选 | 实际做过什么，观察到了什么，结论在何种范围成立 | 概述只保存影响整体判断的结果并链接详细记录；计划、演示和转述不冒充实测 |
| 相关资源 | 有合格资源时填写 | 哪些人、项目、案例或材料值得继续看，具体看什么 | 区分官方说明、示例库、真实项目与商业课程；不按名气或收藏量堆入口 |
| 参考资料 | 有外部断言时必须提供 | 哪条原始材料支持哪项事实或判断 | 优先随论述引用；不必另设重复链接清单，不以搜索摘要代替原文 |

默认正文顺序为概述、问题与原理、适用边界，再接有材料的实践内容和相关资源。其余小节按需要插入；章节数量和篇幅不作为完成指标。

## 问题与原理

这一节承担用户要求的第一性原理分析：从独立于对象宣传的事实、需求和约束出发，再判断对象如何回应。它不是要求为每个实体发明一个“底层本质”。

写作应形成可追溯的解释顺序：

1. 说明没有这个对象时，仍然存在的任务、困难或研究问题。具体描述损失或障碍，不用“提高效率”等泛泛目标代替。
2. 说明完成该任务所需的条件，以及条件为何必要。区分已证实事实、用户要求与为讨论暂取的假设。
3. 说明对象实际采用的机制怎样影响这些条件。每个主要机制至少连接一项前述问题，避免只列功能名。
4. 说明为什么这一方式并非无条件成立：依赖、代价、未解决的问题，以及可能采用的其他方式。仅在有比较依据时讨论替代对象，不编造比较结果。

作者或厂商提出的目标应注明归属；目标不证明效果。历史成因须由历史资料支持，不从今天的能力反推创作者意图。个人理解使用分析表述，不伪装成公认定律。

例如，解释笔记工具时可以先确定“以后能否找回依据并修正判断”这一任务，再讨论保存方式、查找方式与来源联系需要满足的条件，最后核对工具的实际能力。仅说“有本地文件、双向链接、插件，所以适合知识管理”，缺少中间解释，不能通过本节验收。

## 对象差异

现行[实体词表](../../data/vocab/entities.yaml)实际包含软件、编程语言、组织、标准和出版物，内容以技术相关对象为主。`standard` 当前还容纳文档、课程框架与参考站点，写作应核对对象实际身份，不把现行标签直接解释为全部具有规范约束力。

以下调整只改变提问方式，不建立新实体类别。

| 对象 | 原理部分的重点 | 边界与实践重点 |
|---|---|---|
| 软件 | 目标任务、关键机制、设计选择如何解决困难 | 版本、依赖、配置与维护成本；官方建议与实测结果分别说明 |
| 编程语言 | 表达或执行程序面临的问题，语言机制提供什么保证与取舍 | 语言、实现与工具链分开；习惯写法必须有来源与适用情境 |
| 标准与规范 | 为什么需要一致约束，哪些规则服务什么目标 | 标准规定、推荐事项、实现选择与符合性分开；注明版本与范围 |
| 文档与课程 | 面向什么学习问题，内容组织和前置知识如何服务目标 | 内容覆盖不等于学习效果；阅读建议与实际完成情况分开 |
| 组织 | 有依据的职责、公共问题与活动方式 | 不替组织发明宗旨；产品能力归于具体产品，不写组织级操作实践 |
| 人物 | 相关领域的问题、公开贡献与思想或方法的论证 | 不把人当作为某需求设计的产品；不推断私人动机，不写私人信息 |

人物是现行设计允许的类别，但当前正式词表没有人物记录；表中的写法不授权新增人物。对于不适用产品式因果解释的对象，可以使用“主要贡献”等常见标题承载相关问题与论证，仍须说明公开依据及其局限。

## 实践依据

推荐实践须说明谁提出、针对什么环境、解决什么问题，以及为何适用于当前讨论。官方推荐、社区经验与个人验证分别标明；不把某个维护者的个人偏好写成行业共识。只有来源确实提出“最佳实践”时才按其范围转述，正文通常采用“推荐实践”或“使用建议”等常见表达。

个人偏好允许来自用户明确的价值选择，不必伪装成实验结论；但 AI 不得从默认设置、一次操作或没有回复推断出长期偏好。用户尚未深入使用时可以完全没有这一节。

实践结果至少能交代任务、适用版本或环境、实际操作、观察结果与结论限制。详细过程具有独立用途时另写内容，入口介绍只保留摘要和链接。未尝试的建议不写在已验证记录中，不以外部案例代替本人的使用经历。

## 冗余边界

正文中的每段都应能回答：“删掉这段，读者会失去哪项必要认识、判断依据或有价值的入口？”无法回答时删除或合并。

以下内容不进入入口概述：

- 官网已有、且不参与本文解释的安装步骤、完整功能表、参数清单和 API 说明。
- 只换词重复其他章节的价值陈述，或没有具体条件的“强大、灵活、高效”等评价。
- 为填满模板而写的通用优缺点、空白章节、假想偏好和未经实际验证的经验。
- 与本文判断无关的产品历史、插件罗列、版本新闻或人物履历。
- 没有说明参考价值的资源链接，以及用星数、头衔或营销承诺代替的推荐理由。

必要的定义、前提和关键事实即使官网已有，也可以简要转述并附出处。避免重复官网不意味着文章只能依赖外部链接才能读懂；保留量以独立理解本文判断所必需的上下文为限。

概述与详细笔记之间使用链接分工；重复事实只保留理解所需的摘要，不复制整段维护两份。来源变化时，重新核对受影响的判断，不能只更新链接或日期。

## 用语与引用

优先采用已有登记术语、原始来源用语和有依据的行业惯用表达。普通解释使用自然语言，不把日常词组合成新的框架或分类名称。可靠中文译名不足时保留原文；“业内常用”本身也不能代替依据。

沿用[写作规则](../design/governance/writing.md)和[治理规则](../design/governance/governance.md)的术语准入要求。事实、分析和推荐须在措辞及引用上可区分；产品页面支持能力描述，不自动支持效果承诺。对比、领先性与因果效果需要对应证据。

每项关键事实的引用应能定位原始页面、章节或版本。说明实际核对范围，未读材料与已读原文分开；查询结果、别人转述和不可访问来源不写成已核原文。联网或下载权限仍以适用的现行规则与当次授权为准，本草案不扩张权限。

## 写作过程

先确定对象、读者问题和讨论边界，再整理已有依据，选择必要小节并写作。动笔前的范围与依据记录属于工作材料，不强制写进成稿。

重写时按[写作规则](../design/governance/writing.md#过程)列出旧内容去向：保留、合并、拆出或删除；删除理由对应收录边界。新结构不能因为去重而丢失必要前提，也不能沿用已被新证据推翻的判断。

完成后先判断正文是否提供了预定价值，再运行适用的元数据和链接校验。校验通过只证明机器可检查的约束，不替代内容验收。个人偏好、实体归属、正式状态和规则生效继续按各自权限处理。

## 验收要求

只检查可能造成实际损失的失败，不为每个标题、字段回显或章节数量另建测试。

| 要发现的失败 | 后果 | 所需证据 |
|---|---|---|
| 原理部分只有功能与宣传 | 无法理解对象如何解决问题，形成无价值摘要 | 人工核对问题、条件、机制与取舍之间的实际论证及引用 |
| 事实、推断或经验混淆 | 把未验证结论用于选择或实践 | 关键断言与原文、用户表达或真实实践记录的对应 |
| 重复官网或章节互相重复 | 增加阅读与维护负担，掩盖真正判断 | 对照读者问题与来源，说明每段新增的作用 |
| 泛化某个对象的模板 | 把组织当产品、文档当规范，形成错误解释 | 对象真实身份、版本和适用问法的对应 |
| 重写丢失必要依据或条件 | 新结论范围被不知不觉扩大 | 旧内容去向与新结论依据的对照 |
| 元数据或引用无效 | 笔记无法正确检索、引用或维护 | 现有内容校验与应用链接检查，不重复编写包装测试 |
| 草案提前取得效力 | 未批准的规则或数据变成正式约束 | 草案状态、写入范围和人工决定的核对 |

## 写作示例

下面是验收情境，不是外部事实断言，也不直接作为词表或笔记内容使用。

| 情境 | 不接受的写法 | 符合要求的处理 |
|---|---|---|
| 初次认识笔记软件 | 复制功能、快捷键和插件清单 | 解释目标问题、可用机制与代价；操作细节给官方入口 |
| 尚未使用某框架 | “我的最佳配置是……” | 省略个人偏好和实践记录；有出处时保留带条件的推荐 |
| 引用公开示例库 | 因作者知名而声称适合所有人 | 说明材料是示例或真实项目、值得看什么、是否实际试用 |
| 介绍一种标准 | 按软件模板介绍功能与个人设置 | 解释约束的必要性、适用版本、实施条件与解释边界 |
| 调整文章体裁 | 见到一句建议就把解释文章改为操作指南 | 根据全文主要用途与立场判断；独立操作任务另写 |

## 生效条件

本草案需由人确认写作范围、必写要求和验收口径，并明确它与现行写作规则的衔接位置，随后按[草案生效流程](../design/governance/governance.md#变更控制)形成决定并同步适用文档。新增要求的依据应保留为项目决定，不借用外部标准名义。

生效前不批量重写实体介绍，不将本文部署为生成器模板或强制校验，不改变实体、类型、体裁及载体词表。本草案不要求为全部实体批量产文，也不自动接受现有 Obsidian 文章为示范成稿。
