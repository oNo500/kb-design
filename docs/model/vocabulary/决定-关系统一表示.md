# 关系统一表示

状态：方案已采纳，2026-09-12；数据迁移尚未实施。

## 背景

当前主题词表以 `broader` 保存上位关系，实体记录以 `subjects` 保存主题关联、以 `vendor` 保存供应方关系。不同关系分别占用字段，新增关系类型时通常需要增加相应字段及处理分支。

节点可以同时具有多种关系，同一种关系也可以指向多个节点。关系的存储方式可以统一，但各类关系的含义仍需区分。

## 方案比较

| 方案 | 表示方式 | 扩展方式 |
|---|---|---|
| 独立字段 | `broader`、`subjects`、`vendor` 分别保存目标 | 按关系类型扩充字段及处理规则 |
| 统一列表 | 在 `relations` 中逐条保存 `type` 和 `target` | 沿用条目结构，扩充获准的关系类型及约束 |

## 决定

采用统一关系列表作为后续关系表示方案。节点记录中的 `relations` 保存出向关系，每一项使用：

- `type`：关系类型。
- `target`：目标节点的标识符。

关系起点由包含该列表的节点确定。同一节点可列出不同类型的关系；同一种关系连接多个目标时，分别列出关系条目。

这些字段是项目的数据表示选择，不是新增的知识组织概念，也不是外部标准规定的唯一格式。

## 表示示例

以下是既有关系的新表示示例，只说明转换方式，不表示相应数据已经迁移或重新获得采纳。

实体关系的现行表示：

```yaml
id: claude-code
subjects:
  - artificial-intelligence
vendor: anthropic
```

统一表示：

```yaml
id: claude-code
relations:
  - type: subjects
    target: artificial-intelligence
  - type: vendor
    target: anthropic
```

主题上位关系的统一表示：

```yaml
id: machine-learning
relations:
  - type: broader
    target: artificial-intelligence
```

`broader` 仍表示上位概念，`subjects` 仍表示主题关联，`vendor` 仍表示供应方。统一列表不把这些关系改成同一种上下级关系。

## 关系约束

统一格式方便扩展，但不允许任意填写关系类型。每种关系仍需明确含义、允许连接的对象、目标解析方式及适用约束。

新增关系类型仍须经过相应设计与采纳。关系的数量限制、重复处理、逆向关系、循环限制和依据承载方式，应在实施设计中按关系类型确定，不能仅凭通用列表自动推导。

## 实施边界

本决定确定表示方案，不直接切换现行数据合同。

- `topics.yaml` 与 `entities.yaml` 是否合并，另行决定。
- 不因统一表示改变节点身份、关系含义、来源依据或采纳状态。
- `match`、`arrays`、术语关系及其他字段是否纳入同一结构，本次不作决定。
- 本次不修改正式数据、生成输入、schema、校验器或应用消费者。

在完成后续迁移设计前，现行字段继续按既有合同读写；新列表示例不取得当前工具的输入资格。

## 后续实施

实施方案需要列明具体写集，并处理以下问题：

- 既有字段到关系条目的逐项转换，以及对应依据和历史的保留。
- 目标标识符在主题与实体等集合中的解析和歧义处理。
- schema、生成器、校验器、导出器及消费者的一致调整。
- 切换与回滚方式，避免新旧表示成为两个独立编辑源。

主题词表是生成物，实施时应修改生成输入或生成逻辑后重建，不直接编辑生成结果。

## 决策依据

本方案由用户在比较独立字段与统一列表后明确选择，理由是便于扩展。本决定仅记录已选择的表示方式，不宣称关系类型可以免于治理，也不宣称统一格式本身减少了关系数量。

现行职责与数据合同见[主题词表](设计-主题词表.md)和[命名实体词表](../entities/设计-命名实体词表.md)。
