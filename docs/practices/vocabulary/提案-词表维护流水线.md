# 词表维护流水线

本方案把缺词补录、词条修订、版本交付和文章补引用组织成可按需执行、可中断恢复的流程。每项请求携带处理对象、依据、已有结果和剩余工作；步骤只执行满足依赖且仍有必要的任务。

状态为待审工程提案。业务要求沿用[词表维护](../../model/vocabulary/设计-词表维护.md)、[实体设计](../../model/entities/设计-命名实体词表.md)和[词表版本](../../governance/maintenance/设计-词表版本.md)。本文规定工程衔接，不重新定义概念、名称、实体或采纳权限，也不声明功能已经实现。

## 处理流程

```text
维护请求
  |
查找与判断
  |-- 已有适用对象 --------> 复用身份与版本
  |-- 含义或依据不明确 ----> 等待澄清
  `-- 缺别名 / 需修订 / 缺对象
         |
      准备变更与依据
         |
      生成候选、校验、列出影响
         |
      人工确认
         |
      保存维护输入与名称登记、固定词表版本

已有或新生成的适用版本
  |-- 仅维护词表 ---------> 返回处理结果
  `-- 需要应用交付
         |
      核对目标库、按需刷新
         |
      返回身份与可用链接
         |
      请求要求补引用时：文章差异预览 → 按授权补写 → 核对结果
```

已存在的对象须核对字段用途和可用条件，名称命中不等于自动选定。没有数据变更时不重新生成词表；目标库已安装所需版本时不重复刷新。无需翻译、调整分类或建立实体关系时，不产生这些任务。规则要求的完整图及依赖检查仍须保留，不能以“只改一个字段”跳过。

每项请求声明完成目标：仅处理词表、取得指定库中的可用链接，或为指定文章补引用。总览分别报告源端处理、版本交付、目标库安装和文章修改；全部请求目标有核对结果才算完成，取消或不采纳另记结论。

## 职责分工

| 部分 | 职责 | 输入与结果 |
|---|---|---|
| 维护工具 | 组织请求、步骤、依据、确认和恢复，调用各适配器 | 维护请求、具体变更与执行记录 |
| 数据适配器 | 查找、准备和应用指定编辑源的变更，维护身份 | 原版本、候选输入、新版本及维护记录 |
| 校验工具 | 运行适用的结构、图、身份和记录检查 | 固定数据与规则、结果、未检查项 |
| 应用适配器 | 安装词条、返回链接，独立处理获准的文章修改 | 明确目标库、交付版本与写入凭据 |
| 工作流框架 | 处理依赖、持久执行状态、等待和重试 | 已登记步骤及其持久化结果 |

建议以独立的 `kb-vocab-maintenance` 子包承载业务编排，复用现有数据处理包和 `kb-vocab-shacl`，通过 `kb-obsidian-rdf` 接入首个应用。名称与路径是拟定工程接口，不引入新的 RDF 类或属性。

维护请求不属于第三份词表。程序和 AI 可以检索、整理依据、准备变更及诊断；对象判断、具体采纳与发布分别遵守[治理权限](../../governance/decision-making/设计-治理.md#决策权)。框架中的“恢复”按钮不具有采纳效力。

## 编辑源

同一对象的同一属性只有一个当前编辑入口。适配器明确负责的数据范围和基准，不把生成的 TTL 或 Obsidian 页面变成另一个编辑源。

| 数据范围 | 建议的编辑方式 |
|---|---|
| CCS 来源内容与分流 | 保留原件、来源版本和既有分流输入；本地修订另存带基准的变更，不改上游事实 |
| 写作词表 | 继续以 `data/inputs/writing/vocabulary.json` 为编辑源，通过原生成器形成候选与交付 |
| 本地新增概念与实体 | 新设 `data/inputs/vocabulary-maintenance/`，保存本地 RDF 输入、依据及登记，输出时与明确选用的来源一起生成 |
| 类型、体裁、载体及书目 | 保持各自现有 YAML 编辑源与权限，通过相应适配器校验和修改 |
| 文章正文与属性 | 由使用者维护；应用适配器只能执行明确授权的字段变更 |

拟新增目录中，`records.ttl` 保存本地新增记录的当前内容；`edits.json` 保存对导入记录的修订；`names.json` 保存名称身份对应；`changes/` 保存具体变更与采纳依据。名称登记只保存对应关系，不另存一份可独立改写的标签正文。写作输入和既有 YAML 不复制到此目录；CCS 实体也不自动迁入旧 `entities.yaml`。

对导入对象的修订至少包含原身份、属性、完整 RDF 值、比较基准、预期旧值、目标值、原因和依据。文字的语言及数据类型分别保存；同一文字的不同语言不能被一并替换。来源更新时核对基准、新来源与本地意图，冲突交人工处理，不采用最后写入者覆盖。

本地对象、来源对象和名称分别保留稳定身份。已有名称 IRI 不因接入流水线而重算；首次分配与请求修订、名称登记共同保存，重试复用原分配。对未正式采用的候选所分配的身份不授予使用资格，取消后也不转给其他对象。详细身份规则仍由[名称登记](../../model/vocabulary/设计-词表数据规范.md#名称登记)规定。

这些目录和写入接口须经本方案采纳后建立。首次接入先核对既有数据、身份和编辑归属，再固定基准；不直接把当前生成物宣布为可编辑正式数据。

## 请求与步骤

一项维护请求可以关联多篇明确指定的笔记，但不能从正文相似度推定整库文章都应改写。请求可以没有文章位置，例如单独修订词条。以下字段是工程记录，不扩充文章元数据或词表语义。

| 记录 | 必须保存的信息 |
|---|---|
| 请求 | 请求 ID、修订号、原始意图、文字与语境、目标字段或对象、完成目标、范围及依据 |
| 笔记定位 | 库实例 ID、相对路径、内容摘要、可用的文章 UUID、目标字段及期望操作 |
| 步骤 | 步骤 ID、处理器及版本、明确输入、依赖步骤、选用理由、执行状态 |
| 执行结果 | 本次尝试、输入摘要、规则和工具版本、结果文件及摘要、后续需求或等待原因 |
| 确认 | 决定者、时间、依据、请求修订、具体对象与值、候选摘要、允许的目标和写入范围 |
| 写入凭据 | 操作 ID、目标、预期基准、写前与写后摘要、实际结果及恢复位置 |

步骤间传递固定产物的引用及摘要，不传可被任意修改的共享词表副本。结果包括处理结论和有理由的后续需求，例如“对象已存在，只需取得链接”或“缺少依据，需要核对”。

后续步骤只能从已登记处理器中选择，显式保存依赖，拒绝循环。追加翻译语言、来源、对象、目标库或文章写入范围时，必须核对既有授权；不由模型自由生成命令并直接执行。

请求和步骤的执行状态使用工作流框架的能力表示待执行、执行中、等待、成功、失败和取消，不另造一套调度器。旧的成功记录不因输入变化而删除：新请求修订产生新的执行尝试，并说明哪些旧结果已经不适用。未被选用的步骤记录省略理由，不作为已检查事项。

处理粒度为明确对象及属性；名称编辑同时定位语言和名称身份，关系编辑定位两端及关系类型。生成和完整图校验可以按一份候选交付合并执行，共享结果须关联所有适用请求，不能因批量处理丢失单项去向。

## 变更与确认

准备阶段只产生可审阅输入、候选图、差异和检查结果。审阅应能直接看到哪些对象和字段改变、依据支持什么、影响哪些已知引用，以及哪些判断未完成；不要求用户从完整 TTL 中自行寻找差异。

SHACL 检查固定候选图及适用规则，本地条件的对象范围由来源与维护记录确定。名称登记、授权、基准和历史由配套记录检查；实体事实及语义判断单独审阅。未覆盖的必要检查应明确阻止相应交付，不能借普通结构规则通过宣布整个方案符合设计。边界见[规则覆盖](../../../packages/kb-vocab-shacl/COVERAGE.md)。

确认绑定具体请求修订、候选、依据及写入范围。有效的已有决定与批次授权可以复用，同一范围内的机械步骤不反复请求确认。候选内容或范围改变时，先判定原确认是否仍适用；缺少覆盖则重新审阅。比较用摘要防止错用版本，不证明决定人的身份。

词表采用、发布、应用安装和文章补写的权限分别核对，可以一次确认明确覆盖多个动作。文章补写的最终差异仍须满足写前条件；只批准补录某个词条，不自动允许改写所有提及它的文章。

源端写入和正式交付前，再次核对实际生效的对象、值及依据与已审候选一致；确认记录自身引入的差异须明确列出。基准漂移或内容差异不能凭构建成功放行，应重新准备受影响的变更。

生成的开发交付和正式发布分别标识。Git 提交、构建成功、框架步骤成功或目标库存在都不提升数据状态，也不取得正式库写入权限。

## 中断恢复

恢复先核对已保存结果和外部实际状态，再决定复用、续做或重新准备；不能只按上次步骤编号继续。

### 结果复用

纯读取和计算步骤只有在输入、适用规则、处理器及依赖代码版本仍匹配，且结果存在、摘要一致时才可复用。缓存键须覆盖这些条件；到期时间或框架的默认键不能代替。来源字节变化但处理结果未变时，也要核对依据及适用性，不能仅凭输出相同继承原确认。

外部事实查询保存材料、核对时间及适用条件，恢复时依条件判断是否重新核对。输入或规则变化沿明确依赖传递，重新执行受影响部分；未知依赖不能被当作不受影响。整个流程重跑不等于任意旧缓存均可复用。

### 写入核对

每次写操作先持久保存操作 ID、预期基准、写入范围和候选摘要，再执行写入并核对结果，最后保存凭据。操作 ID 在重试中保持；不同变更不能复用同一个 ID。多篇文章逐篇记录，不以最后一篇失败掩盖前面已经成功。

| 恢复时的实际状态 | 处理 |
|---|---|
| 目标仍为写前版本 | 在输入与授权有效时继续该操作 |
| 能证明该操作的目标结果已经写入 | 补齐结果记录，不再次创建词条或追加引用 |
| 部分文件已写入 | 按该适配器的写集和恢复记录完成或恢复；不能当作完整成功 |
| 目标有无法解释的变化 | 保存现场，报告冲突，重新准备相应变更 |
| 确认或材料已不适用 | 等待重新核对，保留此前的结果与历史 |

维护输入、名称登记和变更记录共同构成一次源端操作。其适配器必须具备互斥写入、写前比较、完整暂存、操作记录及恢复核对；名称登记不能先成功而输入失败后又重新分配。只有完整写入集合相容时才允许下游读取。

词表版本、库内词条和文章分步提交，不宣称跨文件、跨目录或跨系统事务。现有工具锁只协调本工具；文件写入阶段须暂停目标库的其他编辑与同步，源端写入同样须排除其他写入者。未知并发不能靠一次摘要比较或文件替换承诺安全。

### 失败与取消

短暂的读取故障或可安全重试的计算错误，可以有限次重试；规则失败、语义歧义、权限不足和并发冲突保留原因，等待处理。人工等待应保存结果并结束本次执行进程，之后通过同一请求恢复。

源端完成而应用刷新失败，保留源端成果并恢复刷新；刷新完成而补引用失败，保留已安装版本并恢复文章操作。后续失败不自动撤销前面的采纳，不通过覆盖用户内容来恢复词表。

取消停止尚未执行的工作；正在写入的步骤先完成状态核对并保存凭据。已经成功的修改如需撤销，形成独立、有依据的变更。整项请求未完成时仍列出已写入的对象和位置。

## 文章衔接

请求可在返回对象身份、目标库实际版本与可用链接后结束，也可继续执行指定文章的补引用。正文链接、元数据引用和文章登记是三种操作，分别说明结果。

### 笔记定位

`inbox/` 中的自由笔记不要求 UUID 才能提出请求。保存库实例、路径、内容摘要和必要语境；有文章 UUID 时以其核对身份，路径仅作定位。没有 UUID 的文件发生移动或内容变化而无法确认对应时，要求重新关联，不按名称或正文相似度自动改写。

缺词任务不会自动给自由笔记加入 `identifier`，也不迁移目录或补造分类。自由笔记可以只取得链接。若要求登记为受控文章，另行预览必需字段、身份及目标位置，明确确认后登记，再补引用并校验；不得把当前的“新建文章”接口当作既有笔记登记接口。

### 引用补写

补写计划固定文章身份或明确关联、预期内容摘要、目标字段、选定对象身份、采用版本和修改前后值。默认新增指定引用并保留已有值，去重按对象身份，不能用字符串不同制造同一对象的重复引用。替换或移除已有值须有相应意图和授权。

写前核对实际安装版本、对象类别、字段值域、可用条件及当前文章。文章或交付变化时重新生成差异，不覆盖新编辑；基数为单值的字段发生冲突时不能按列表追加。实现须保留正文及未涉及属性的内容和格式，避免整体重排文件。

文章登记和引用补写都先形成最终候选文件，解析其实际字节，完成适用的字段、完整文章模型及引用校验后才允许写入；校验失败保留原文件。不能只验证内存中的部分字段，再把未经检查的序列化结果覆盖到文章。

每篇写入后核对实际结果与候选一致，检查真实字段和引用，并确认已登记文章可由明确身份找回。程序不能把正文提及当作 metadata 已写入，也不能将未登记笔记报告为文章校验通过。写入结果不明时用操作凭据和目标实际值核对，不能盲目重试。

## 工程接口

以下是需要实现的接口职责，不是当前已经可执行的新命令。默认操作生成预览，真正写入使用明确目标和已覆盖的授权。

| 操作 | 必须给出的结果 |
|---|---|
| 提交请求 | 请求 ID、修订、目标和已固定的原始输入 |
| 查看进度 | 已完成结果、剩余依赖、等待原因、部分写入与下一步 |
| 准备变更 | 查找结论、候选输入、校验、影响和可审阅差异 |
| 登记确认 | 与具体候选和范围对应的决定引用，不仅一个布尔值 |
| 执行与恢复 | 核对已有结果后执行剩余步骤，返回各写入凭据 |
| 取消请求 | 取消范围、仍需核对的写入以及已经发生的变化 |

数据适配器提供查找、准备、校验、应用、实际结果核对；应用适配器提供版本检查、刷新、链接解析和独立文章补写。编排器调用这些能力，不直接拼 shell 命令编辑各包文件。上下游通过固定版本的记录接口交换数据。

现有接入点按 2026-09-23 的代码核对：

| 接入点 | 已有能力 | 本方案要求补齐的部分 |
|---|---|---|
| `kb-vocab-ccs` | 原件固定、转换、分流和独立校验 | 本地修订接入、名称连续性、退出及历史登记 |
| `kb-vocab-writing` | 结构化编辑输入、带依据生成、确认摘要与校验 | 请求及执行记录接入，精确应用获准变更 |
| `kb-vocab-shacl` | 字段结构、统计及多组规则 | 按变更来源传入明确对象和所需上下文；未覆盖管理要求另作检查 |
| `kb-obsidian-rdf` | 查词、检索、生成、刷新、检查及中断恢复 | 用显式版本清单替代 `prepare` 固定目录；既有笔记登记、引用差异与补写 |
| 维护编排 | 尚无贯通上述路径的实现 | 请求持久化、按需依赖、确认绑定及整条流程恢复 |

旧 `kb-vocab` 的维护接口服务另一条既有生成路径，不因名称相同就视为本流程已经接通。上述差距用于安排实践，不减少业务设计要求。

## 运行方案

优先验证 Prefect 的本地部署方案，复用框架的步骤状态、依赖、持久结果与人工等待。Python 的条件分支适合组织按需路径；跨进程等待采用具备部署和结果持久化条件的 suspend，不能用仍依赖原进程的 pause 冒充中断恢复。[Prefect Flows](https://docs.prefect.io/v3/concepts/flows)、[暂停与恢复接口](https://reference.prefect.io/prefect/flow_runs/)

Prefect 的结果持久化与缓存策略需要显式配置。默认缓存键含本次运行 ID，任务源码键也不覆盖所有被调用代码，因此必须按[结果复用](#结果复用)构造依赖指纹。框架复用计算结果，数据适配器仍须核对外部写入。[Prefect Caching](https://docs.prefect.io/v3/concepts/caching)

Temporal 作为备选：通过事件历史重放恢复工作流，可用消息及等待条件接收人工决定，但需要 Service、Worker 及满足重放要求的工作流代码。已记录完成的 Activity 不因重放重做，外部操作成功而完成回报丢失时仍可能重试，不能据此承诺文件只写一次。[Workflow Execution](https://docs.temporal.io/workflow-execution)、[Python 消息机制](https://docs.temporal.io/develop/python/workflows/message-passing)、[Activity Definition](https://docs.temporal.io/activity-definition)

两者都是工程机制参考，不是词表标准，也不替代采纳权限。上述官方材料核对日期为 2026-09-23；本轮未安装、运行或完成依赖准入。实施前按 Library-First 约定核对具体版本、维护状况、安全记录和安装影响，以重启后等待恢复、结果复用及写后中断三个场景确定能否采用；不因未选框架而先自建通用调度器。

持久请求、执行结果及框架状态全部在库外管理，建议业务运行资料使用 `output/vocabulary/maintenance/<request-id>/`。其产物按步骤、修订和尝试区分，结构化记录可用 JSON Schema 校验；最终词表仍是 RDF/Turtle。该目录属于持久状态，不能随 `build/` 清理；框架状态与其引用的产物一起备份。可重建的索引不得成为身份、确认或历史的唯一记录。

状态缺失、产物损坏或版本不相容时明确停止相应步骤。恢复保证以实际持久存储、备份和适配器验证范围为限，不宣称保存 Python 内存、跨机器自动恢复或断电后所有写入仍持久。

## 验收场景

每项验收针对不同失败后果，避免用重复计数或文件存在代替行为证据。

| 场景与失败后果 | 独有证据 |
|---|---|
| 已有对象仍被重复创建，或同名对象被错选 | 既有身份复用；歧义停在待选；无新增数据操作 |
| 新增实体导致旧名称换号或新名称重试换号 | 固定基准与两次执行后的身份登记、具体差异及原名称引用 |
| 候选变化后沿用旧确认 | 变更候选或依赖后的拒绝记录及重新审阅结果 |
| 源写入成功、记录结果前中断导致重复变更 | 注入该窗口的中断；重启核对实际写入，补凭据且不重复操作 |
| 刷新成功、文章补写失败导致误报完成 | 分别报告安装成功和文章待处理；恢复后只完成必要补写 |
| inbox 文件移动或文章被修改，导致误写 | 无法确认位置或基准时不写入；重新关联后生成实际差异 |
| 文章登记或引用补写形成无效字段组合，先覆盖再报错 | 最终候选文件在写前校验失败，原文件未被替换 |
| 相同请求重跑导致重复引用或正文变化 | 引用按身份只保留一次；正文及无关属性保持原值 |
| 重启或缓存缺失导致错误跳步 | 持久状态与产物核对；缺失结果重新计算，未知写入先核对 |
| 取消被误当回退，或局部失败覆盖用户内容 | 保留已完成操作，列出未完成目标，不回退文章新内容 |

首个完整案例为“补录 Obsidian 软件实体，交付到开发库，再为一篇已登记笔记补 `entities` 引用”。其具体来源、实体记录和文章仍需独立核对；示例不自动批准数据。另用一篇无 UUID 的 inbox 笔记验证只返回链接和明确登记两条路径。

## 实施次序

先完成请求记录、数据编辑归属与名称登记，再接入候选生成、校验及确认；随后实现持久编排与中断核对，最后接通版本选择、应用刷新和文章补引用。完整案例贯穿各阶段，避免只证明单个包能运行。

新增、修订名称、调整关系和停用共用本流程，但各自采用既有维护语义。批量翻译、来源大范围更新、概念合并拆分和多应用交付可在相应权限下接入，不因流程存在而默认启用。库外状态布局、框架依赖和新编辑源的正式启用随具体实施方案审阅，不在本提案中自动迁移现有数据。
