# 写作规则

本库所有 Markdown 文件的写作规则，按 ISO 24495-1 的 4 条原则组织：相关、可找到、可理解、可使用。每条规则标出处；没有出处的规则不收。理论见[写作规范](writing-conventions.md)，依据的整理见[写作规范阅读笔记](reading-writing-guides.md)。

`AGENTS.md` 是本文的摘要。designation 的准入与译名规则以[治理](../decision-making/governance-rules.md)为准；术语概念、定义和形式由 `data/vocab/terms.yaml` 管理，`docs/glossary.md` 是只读生成页。主题、载体及模型标签输入保留各自的编辑权，详见[术语设计](../../model/terminology/terminology.md)。

## 文档类型

动笔前先确定读者的问题和文章职责。同一主题内的概念、设计、依据、决定与提案分别成文，由主题首页关联。

| 文档 | 职责 | 表达要求 |
|---|---|---|
| 概念解释 | 解释含义、机制和适用边界 | 可以讨论、比较和举反例；项目选择链接现行设计 |
| 现行设计 | 规定项目当前的对象、关系和规则 | 克制准确，必要的定义解释不代替规则 |
| 决定记录 | 保存背景、决定、状态与后果 | decision- 前缀；历史记录只追加，旧路径按原基线解释 |
| 阅读笔记 | 保存来源事实、阅读位置和核对范围 | reading- 前缀；个人判断独立标明，不冒充原文 |
| 项目提案 | 说明待议问题、方案和生效条件 | proposal- 前缀；部分另行采纳不等于整体生效 |
| 操作指南 | 帮助完成具体任务 | 先说明条件，再给步骤和可核对结果 |
| 主题首页 | 按问题导航至相关正文 | 说明收录范围，不复制各篇规则与动态进度 |

目录按项目主题组织，文档职责和效力分别识别。前缀只是分类入口，不能使不合格依据、未采纳提案或 schema 记录取得授权。

## 内容相关性

| 规则 | 出处 |
|---|---|
| 一篇文档只服务一类需求，不混 | Diátaxis |
| 不预告（“后面会讲”“即将支持”） | Google highlights |
| 待办、待定统一放文末“待定事项”或“待办事项”节，不混进正文 | 本库，由“不预告”推出 |
| 新增或修订的内容直接写成定稿，不在正文留“待写”“TODO” | 本库，同上 |

| 规则 | 出处 |

| 不用“**加粗词**：”冒充标题层级 | Google headings（不用格式改变层级） |
| 引用一组小节说“以下各节”，引用某节用标题名，不用序号 | Google headings |

## 表达规则

| 规则 | 出处 |
|---|---|
| 一般 designation 按治理的来源阶梯检索并在其现行编辑源登记；无依据时不由 AI 自定。既有概念的译名可按已开放的第 5 级使用模型既有知识，明确记录模型判断及外部用法未核实；不据此创造概念、类别或划分特征 | 本库；[治理](../decision-making/governance-rules.md#译名)、[模型知识译名](../../model/terminology/decision-model-knowledge-translation.md) |
| 同一概念全库一种写法；英文术语首次出现时中文后括号给英文，此后只用中文；单篇长度不设上限，由“一篇一个问题”约束 | 受控词表；Google word list 的做法 |
| 中文句子用全角标点；整句英文用半角 | GB/T 15834 §4 |
| 引号用“ ”，内层‘ ’；不用 `「」` | GB/T 15834 §4.8 |
| 补充说明用全角圆括号（ ）；方括号、六角括号、方头括号按 §4.9 的用途 | GB/T 15834 §4.9 |
| 破折号——、省略号……各占两字位 | GB/T 15834 §4.10、§4.11 |
| 连接号：号码和复合词用短横线-；起止用一字线―或“至”；数值范围用浪纹线～ | GB/T 15834 §4.13 |
| 汉字与西文字母、数字之间加一个半角空格；西文或数字与全角标点之间不加 | clreq §6.3.3（间距不超过四分之一汉字宽，空格为 Markdown 中的实现） |
| 第二人称“你”，不用“我们” | Google highlights |
| 主动语态，说清谁在做 | Google highlights |
| 句首大写（sentence case），不用 Title Case | Google、Microsoft |
| 英文并列用序列逗号 | Google、Microsoft |
| 去掉弱写法；不用口语强调语（“一句话”“说白了”“其实就是”），直接陈述 | Microsoft top 10；Google 的 conversational but not frivolous |
| 外部事实核对原文后才提交；本阶段只用已有离线资料，不联网或新增下载，未核实事实如实标明。经授权的译名第 5 级按模型知识登记，明确外部用法未核实 | 本库；[模型知识译名](../../model/terminology/decision-model-knowledge-translation.md)、[语言依据结构](../../model/terminology/decision-structured-label-basis.md) |

结构化语言依据中的第 5 级必须在可读表示中保留模型知识及外部用法未核实的声明，不能只显示译名或把判断当外部引文。术语中英形式在 `data/vocab/terms.yaml` 登记；主题与载体的采纳输入保留原编辑权。

形式依据、概念对应依据和具体断言依据分别核对，任何一项都不能替代另一项。普通叙述、来源转录、文件路径、代码和值中的字符串不因首次出现自动成为项目采用的名称；`candidate`、`defer`、草案、占位、示例、schema 状态和迁移去向也不能取得试用资格。

`uv run kb-core check-terms` 从 Git 中取得动态 Markdown 清单，检查标题、加粗内容和中文引号，排除代码围栏、行内代码、链接目标和路径；默认与 `docs/glossary.md` 及现行主题、实体、类型词表中的已登记写法比较。输出保留精确位置和上下文，只是 `report-only` 人工复核材料。命中不形成 designation、概念、关系、违规、阻断或候选记录；人工拟采用某个命中时，仍须走现行准入阶梯。

`data/audit/migrations/term-v1/terms.tsv` 只继承冻结审查与消费者去向，不是术语词表。正式术语记录与参考发布按已采纳决定启用；义务、委托和草案中的未来周期不因数据或生成能力存在而生效。

划分特征草案提出的零自定例外尚未开放；已开放的模型知识译名只作用于既有概念的语言表示。草案中的属性名在实际采用前仍须按治理规则由人决定。

## 使用条件

| 规则 | 出处 |
|---|---|
| 参考类只陈述；解释类才讨论 | Diátaxis reference、explanation |
| 条件放在指令前面 | Google highlights |
| 表格前用完整句子说明用途；表头简短、不以标点结尾；不合并单元格；只有一行或一列不用表格 | Google tables |
| 示例用代码块，不用文字描述“形如……” | 本库，由“可使用”推出 |
| 日期用 ISO 8601 | Google highlights（日期无歧义） |

## 写作过程

以下规则管写作过程；依据是本库实践及用户明确采纳的内容要求，同步摘要到 `AGENTS.md`。

- **内容先于篇数。** 写作前明确读者要解决的问题、相较原始资料新增的价值，以及适用的文档类型；说不清楚就不建文章。正文必须履行该类型的要求，不得用泛泛建议冒充操作指南。
- **组织依据明确。** 优先使用现有主题、实体、文档类型和载体组织内容。索引必须有明确的收录范围和查找依据。现有模型不能表达需求时，先提出设计缺口，不临时创造分类。
- **入库前审阅。** 分别检查内容价值、类型符合性、组织合理性和元数据有效性。字段校验通过不能代替前三项。批量写作先完成一篇样稿及索引示例，经用户确认后再扩展。

- 改文章不打补丁。改动涉及一节以上时，整节或整篇按目的重写
- 重写或拆分前，先列旧版逐节去向；写完逐项核对，确认没丢
- 重写是发现空缺的手段：补丁掩盖的缺口在重写时暴露，暴露了就补
