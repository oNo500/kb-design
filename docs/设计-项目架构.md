# 项目架构

kb-design 维护共享的知识组织模型、正式数据和处理程序。具体应用读取这些模型与数据，规定内容在目标工具中的表示与使用方式。项目由来和范围见[项目概述](概述-项目.md)。

## 系统边界

本仓库保存设计、词表、术语、依据登记和配套工具；新的正式知识库位于仓库外的 `~/Documents/knowledge-base/`，原 `~/Documents/kb-vault/` 保留为旧库。知识内容的身份、主题和引用由共享模型规定，实际文件与交互由应用实现。

人负责范围、采纳和正式状态等决定；程序执行生成、校验、读取和报告。程序能表示某个字段或生成某个结果，不因此取得采纳权。具体权限见[治理](governance/decision-making/设计-治理.md)。

## 模型与数据

| 对象 | 设计职责 | 编辑源 |
|---|---|---|
| 内容 | 字段、稳定身份、引用与生命周期 | [内容模型](model/content/索引-内容模型.md)；实际内容保存在知识库中 |
| 概念词表 | 概念的名称、定义、别名、翻译与关系，供主题标引及分类浏览 | `data/inputs/topics/` 和核心生成实现；输出为 `data/vocab/topics.yaml` |
| 实体记录 | 具体人物、组织、项目、产品等对象的身份、属性及有依据的主题关联 | `data/vocab/entities.yaml` |
| 文档类型、体裁、载体 | 内容各字段的受控值 | `data/vocab/types.yaml`、`genres.yaml`、`forms.yaml` |
| 术语 | 概念、定义、多语名称、依据和历史 | `data/vocab/terms.yaml`；布局另由 `data/inputs/terminology/glossary-layout.yaml` 管理 |
| 文献与来源 | 文献身份、获准用途及具体引用依据 | `data/references/bibliography.yaml`、`data/vocab/sources.yaml` |

概念词表与实体记录是两项管理职责，不是对所有名称作二选一分类。需要同时管理某对象的主题与事实时，分别维护身份并关联；不因同名自动合并，也不为每个概念强建实体。职责见[概念词表](model/vocabulary/设计-词表整体设计.md#对象分工)与[实体记录](model/entities/设计-命名实体词表.md#对象分工)。

词表中的名称与术语形式分别维护，名称相同不构成编辑权委托。术语表 `docs/参考-术语表.md` 是只读生成页。完整对象关系分别见[知识模型](model/索引-知识模型.md)中的主题入口。

## 程序职责

| 部分 | 输入与职责 | 边界 |
|---|---|---|
| `packages/kb-core/` | 读取共享数据、生成术语参考、校验依据及决定、产生诊断 | 不依赖具体应用；主题生成入口转交独立包 |
| `packages/kb-topics/` | 读取主题生成输入和已采纳依据，生成正式主题词表 | 依赖核心校验能力；不调用具体应用 |
| `packages/kb-vocab-maintenance/` | 收录旧实体资料、比较 RDF 字段、准备及应用带基准的描述字段修改 | 止于词表交付；不更新应用或文章，不使候选转正 |
| `apps/vocab-preview/` | 读取工作区词表与书目，提供搜索、关系和依据浏览 | 只读；可以展示未提交数据，不表示数据获准 |
| `apps/obsidian/` | 读取干净设计快照，初始化旧合同知识库、导出与刷新参考、建立和校验内容 | 继续服务原有实例；不决定新开发库布局 |
| `apps/obsidian-rdf/` | 固定 RDF 及辅助输入，生成独立编号 PARA 开发或正式实例，分别维护词条交付与应用配置 | 正式新建依具体采用范围；不借刷新改变模式，不自动迁移旧库或编辑文章 |
| `packages/quietpaper/` | 维护 Obsidian 主题源码、构建及显式目标部署 | 独立 Bun 包；只负责显示，不改变模型、词表或文章 |
| `scripts/` | 整仓文档链接等辅助检查 | 不承担正式值的采纳 |

Python 工程使用根 uv workspace 与统一 `uv.lock`；Quietpaper 使用独立 Bun 工程与包内锁文件，边界见[主题包接入](development/决定-主题包接入.md)。开发入口见[工程开发](development/索引-工程开发.md)。

## 数据流转

主题修改从生成输入和 `packages/kb-topics/` 的生成实现开始。生成器读取已采纳的来源与标签输入，产生 `topics.yaml`；修改者核对差异并执行相应校验。直接修改输出会在下一次生成时丢失。

术语修改从 `terms.yaml` 开始。生成器核对概念、名称、依据及具体采纳，以布局输入生成 glossary 和参考表示。布局决定展示，不承担概念和名称的编辑权。

旧实体收录保持 `data/vocab/entities.yaml` 为编辑源，持久登记对应身份，生成保留原状态、依据与未投影信息的 RDF 交付。本地修改以固定基准和明确计划生成新交付；词表完成不自动使应用加载新版本。

应用读取共享数据后进行表示转换。词表预览使用工作区文件；旧 `kb-obsidian` 使用干净 Git 快照；新 `kb-obsidian-rdf` 使用明确输入清单及其固定摘要。各应用记录实际采用的数据与版本，不能互相推定已经更新。

词表维护、应用产物维护和内容维护分别执行。应用可以显式选择词表交付，配置或视图维护不自动换词表；文章所选引用需要独立的内容操作。工程分工见[词表维护](practices/vocabulary/设计-词表维护工程.md)和[Obsidian 产物维护](applications/obsidian/设计-产物维护.md)。

## 应用边界

[共同适配要求](applications/shared/索引-共同适配要求.md)规定共享模型、Application Profile 和导出合同的分工。[Obsidian 适配](applications/obsidian/索引-Obsidian%20适配.md)规定具体属性、链接、目录与操作；[词表预览](applications/vocab-preview/索引-词表预览.md)规定工作区浏览行为。

DITA 在现有内容模型中提供设计参照。将共享内容输出为 DITA 是可能的目标，需要独立的适配设计；现有引用不表示已具备该输出能力。

Obsidian 参考刷新更新约定的受管理区域，保留用户内容与配置。编辑应用中的生成文件不回写正式数据；内容消费者、查询日志和回流仍受各自启用条件约束。

## 文件职责

`docs/` 按项目主题组织说明与设计；词表的目标设计位于 `docs/model/vocabulary/`，现行合同、实现与操作位于 `docs/practices/vocabulary/`。目标设计依据标准和需求制定，实践遵循设计；问题须经记录、研究及相应采纳后才能形成新设计。每个主题入口区分设计、实践、概念解释、阅读依据、决定和提案。“决定-”“阅读-”“提案-” 分别标识后三类文档；文件位置与名称不构成采纳。

`data/` 保存正式数据、生成输入和审计材料，各自效力按模型规定。`work/` 保存计划、复核与执行历史；`output/` 保存持久应用数据；`build/` 保存可清理的临时产物。后两者由 Git 忽略，清理构建产物不触及持久知识库。

## 关键约束

- 稳定身份不从显示名称、目录位置或排序推导。
- 依据、实际派生、概念映射和项目授权分别核对。
- 草案、诊断和迁移账本不取得正式数据效力。
- 应用输出成功不等于外部知识库同步、消费者启用或发版。
- 历史决定与依据中的旧路径按形成时的 Git 基线解释；[文档迁移清单](../work/plans/2026-09-12-docs-topic-files.json)提供当前位置，不改写历史采纳值。

当前工作见[项目路线](../work/roadmap.md)，具体规则从[项目文档](索引-项目文档.md)按主题查阅。
